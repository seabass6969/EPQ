\chapter*{Abstract}
\textit{For the purpose of this project, the replica of a music recognition app is created.}\\
\textit{The algorithm first creates a fingerprint for each audio file in its spectrogram. Which are added to a database as a hashed value.}\\
\textit{When song are recorded through the interface, the algorithm repeats the fingerprinting process, but instead compares the hash value with the matched songs.}\\
\textit{During the research phase there are multiple areas that require extra research, such as testing the program and solving unexpected errors.}\\
\textit{At the end, the artefact are created to fulfill the original goal of recreating it.}

\section{The algorithm}
When the program first registers the song in to the database. It will go through the process of "fingerprinting" to the piece of music. The algorithm consist of creating spectrogram where it uses STFT (Fast Fourier Transform dissolves a function of time or signal into the frequencies that makes in a way similar to how a musical chord can be expressed as the pitches of its constituent notes. It is also called the frequency domain representation of the original signals. Short-time Fourier Transform is a variation of the Fast Fourier transform built for making spectrogram \footcite{alpay_short-time_2024}). Illustrated in the appendix figure of \autoref{fig:fft}. \footcite{chittora_brief_2018} 

In this case, The spectrogram is being filtered through using maximum filter. The two spectrograms are compared to pick peak points. The peaks used to construct the pairs. The pairs of points are hashed using the default hashing function (Hashing function is a function where you put in any item and getting back a number. Hash functions' output tells you where the item is store and the item can be searched in a very fast time. \footcite{bhargava_grokking_2016}) which generate an almost unique hash values in the program.  Illustrated in figures in the appendix \autoref{fig:listfiltering}, \autoref{fig:hash} and \autoref{fig:pairspicking}.

The hash point is then placed into a database alongside with its song name and where the point A's real time. The song data (metadata) such as author and copyright detail are placed in a different database. Database example: \autoref{fig:main:database}.

When the user record the sample of audio through the user interface from the web app, the recording sample is sent to the server. It is processed where it applies the same algorithm from above. First it constructs a spectrogram, peak point are picked and hash values are created, the hash value are searched inside the $points$ table. The points table are as illustrated in \autoref{fig:hash}.

The list of successfully matched song are than going through the process of "scoring". The score calculated by constructing a histogram with the point A's real time value. (As illustrated in the forth column of \autoref{fig:hash}) The highest score would be the correctly matched song. Using score system ensures accuracy results. \footcite{wang_systems_2013} \footcite{macleod_abracadabra_2022} \footcite{yang_music_2001} \footcite{wang_industrial-strength_2003}

\section{Coding section}
The hardest part of creating this artefact is programming the algorithm of the program. From using the blog post source (\cite{macleod_abracadabra_2022}). It leads me to the direction of creating the algorithm that takes in the song file and fingerprint the song entry in the program. 

Within the scope of the project, Python are chosen to program the algorithm, as Python is the most popular programming language for data analysis and other general usage.

Initially, a problem appeared where there are two different song arrays. Later found out that because most song file are represented as stereo music (where there are typically two channels eg.: left ears and right ears). So a music encoding program of FFmpeg is used to mixed the audio back into mono audio. Unfortunately, Shazam\trademark does not explicitly provide the information on how they handle stereo music, as stereo music are prominent at the time of the patent are published. 

From the research into the method of creating spectrogram, due to the time constraint of this project, creating an algorithm that produces a spectrogram is not possible. A programming library is used to produce spectrogram instead of creating the spectrogram algorithm from scratch. Next the spectrogram are initially programmed so that it is produced using the librosa library. However, due to the constraint created by the library librosa and the low efficiency that the library creates, within the design it is require to be "high performance", so the signal library Scipy are used instead\footcite{virtanen_scipy_2020}. The spectrogram produce by SciPy are illustrated in \autoref{fig:spectrogram}. And the data are processed using the library of NumPy \footcite{harris_array_2020} through maximum filter in the library of SciPy \footcite{virtanen_scipy_2020}. The output of two arrays of spectrogram data are compared using NumPy's technique of boolean mask as shown in the figure in \autoref{fig:listfiltering}.

When the pairs are created from the peak picked from the maximum filter, the patent included methods to create pairs of points. However, the patent does not specify what is the upper and lower limit of how pair of points should be spaced each other. From different testing, it have suggested that the upper limit of $4000 Hz$ for the frequency and $1.5 second$ of time the pairs of points limited to. 

In addition to the upper limits, the lower limit of $0.05 second$ to prevent pairs to be too close to each other. 

Having upper limit allows the program to not create too many pairs of values, as if there are no limits to how many pairs there are, there would be way too many pairs created, which reduces the uniqueness of each fingerprint profile of each song. And it reduces the performance of searching as there are more fingerprint entries in the database. For example: one of the song \textit{J. S. Bach: Prelude in C - BWV 846} when there are noises added to the original sample, there are $2138 \text{ peaks}$, if no upper limit is imposed, there would be $2138 \times (2138 - 1) = 4568906\text{ pairs}$ (which is about the half the size of all the pairs stored in the actual song database for all the songs which is about 65 songs) and way larger than the final with limit of $8668 \text{ pairs}$ for the song. 

Having lower limit allows points that are nearly next to each other to be omitted from pairing up, as some recording, there are imperfection in intonation or sound attenuation over distances when recording.

It was also discovered that from creating the program, rounding up the frequency and the time value are required for the algorithm to work properly. This is discovered during the creation phase of the project from the discussion with the professional (\autoref{section:meeting:pro}). This might be due to different microphone in different device records slightly differently, and their electrical design might be different. And as sound wave propagates for some distances through the atmosphere, high-frequency components become more attenuated than low-frequency ones due to heat conduction, shear viscosity, and relaxation losses. This is noticeable after $>15 \unit{\meter}$. \footcite{spiousas_sound_2017}

\section{Extra investigation}
During the creation process, the project encounters a hurdle. Due to random noise in the sample of the audio during the fingerprinting process, it was unable to block the random noise in the sample, because of this when the program is sampling "Nothing" just background noise, it would appear to the user that there is song playing in the background with a random results because the program only initially took the maximum value from the list of scores. This is not mentioned in any of the articles. (This might be due to the quality of the songs)

Investigation and experiment is done to fixed the problem. The problem are fixed by using a mathematical concept of finding outliers from the list of songs. Firstly, all the score are fetched from the searching done inside the database. Then, the interquartile range would be calculated from the list of data. If there are an outlier, that means that the matched songs are not created by random background noise from the sample itself. See \autoref{fig:error:screen}

There are also places where errors are circumvented, such as at the start the user can record sample of the music that have a short duration, this would not be effective as the program would not be able to recognise songs. So an error prompt message is added to stop the user from uploading a song that is too short. See \autoref{fig:error:screen}.

\chapter{Testing method}
The program is tested using the method described in this paper \footcite{yang_music_2001} and a primary research conducted from a meeting of a \hyperref[meeting:2]{professional}. An evidence from all the song from (almost 100\%) of the fingerprinted music collection is used to test the program, this is so that it reduce the likelihood of a flawed test. 

The test have increasing level of difficulty:
\label{chapter:test_methods:methods}
\begin{itemize}
    \item Test 1: original song file (unmodified digital file)
    \item Test 2: original song file but shifted 
    \item Test 3: original song file but with controlled level of noise. (E.g.: a sine wave)
    \item Test 4: original song file but played over the air and recorded.
    \item Test 5: original song but perform by different people.
    \item Test 6: transposed song \label{t:test_transposed}
\end{itemize}

Test 1, 2 worked 100\% of the time. Test 3 worked 74\% of the time. However because test 4 requires a lot of time I only tested 40\% of the data but most works. (There are some anomalies because for some reason the song database have duplicate songs.) Test 5 and 6 are not tested extensively because it's time consuming and it is expected that most of them fails so at the end only just 10\% of the songs are tested and all of them did failed.

There are also additional tests one where there are no audio playing, just background noise, this is done for control purposes.

The test results is inside \autoref{fig:table_of_testing_result}.

In addition further test should be done to test the program on performance , as Shazam\trademark's end goal is to create a high performance algorithm, and I haven't tested on this aspect yet. This could be tested in various different ways, such as testing it using more clients and more traffic flow, I could also test it with more number of music in the database. 

\chapter{Discussion}

As discussed in \hyperref[t:test_transposed]{the test conducted}, this artefact is not capable to detect a transposed music, "humming", live music and a piece of music being played by a different orchestra. Because this song only matches the exact frequency that the song produces. 

One way that the problem can solve is to change the fingerprinting and searching mechanism entirely to not rely purely on the raw frequency data, instead by using the MIDI file (where it uses MIDI messages that control musical elements like pitch, velocity, modulation, and more. \footcite{anthony_what_2025}) Then from it, create a database of melody. Which can recognise songs from it by recording the song and passing the fingerprint of the recording into the algorithm to process for results. This allows a wider error range for recognizing song such as it can it capable of detecting recording made from "humming". \footcite{ghias_query_1995}. However, this would make the algorithm costly and slow to run. \footcite{yang_music_2001}

In addition, extra research might be needed to improve the speed, making it more commercially viable which is the goal set out by the Shazam\trademark team where they designed it so that it's high performance. \footcite{wang_systems_2013}

The research can also be further extended not limited to searching for songs, such as searching for patten inside text, audio, video, image, and any multimedia combinations of individual media types. For example: image fingerprints can be created from an array of pixel's RGB value. \footcite{wang_systems_2013}

In addition, this project only uses copyright-free music, as there would be legal and ethical implication to using contemporary music.

The biggest ethical implication that most music recognition app faced are privacy violation, as some app record the audio in the background even without user interaction. The project would not be concerned about this because it only records when user intended to. So a privacy notice is created to show to the user if needed. And there are also privacy notice created to tell the user the retention period of the data, which is set to 30 days and the data would be kept anonymously. For more details, please scan the QR-code for privacy notice from \autoref{chapter:links}.
